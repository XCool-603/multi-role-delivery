# 多角色组队交付

把一个任务跑成一条流水线：

**接单拆解 → 多角色并行干活 → 产品独立验收 → 返工直到通过 → 统一交付**

每个阶段都有落盘产物，全程可追溯。用户只说任务，不说要哪些角色——角色由你判断。

## 四条硬性规则

1. **不问角色。** 用户不会告诉你"要哪些角色"。你拆解完自己定，并在 `plan.md` 里说明理由。只有交付物本身有歧义时才回问用户。
2. **验收者必须独立。** 产品/QA 不能是任何一件交付物的产出者。它是另一个代理。
3. **证据只看盘上的东西。** 子代理的自述不算验收证据。验收必须读真实产物、真跑命令。
4. **没通过就不说完成。** 只有验收 `pass` 才能进交付阶段。返工到通过为止；遇到平台期（见阶段 3）才停下来向用户升级。

## 任务目录

接到任务后**第一件事**就是建目录：

```
<cwd>/.dsh-team/<task-slug>/
├── plan.md              # 阶段0：拆解、角色卡、验收标准
├── work/<role>/         # 阶段1：各角色的真实交付物
└── review/round-N.md    # 阶段2/3：每轮验收报告
```

`<task-slug>` 用短 kebab-case（英文或拼音），例如 `cli-json-tool`、`baogao-paiban`。

## 阶段 0：接单与拆解

**先定义"完成"。** 把交付物写成一两句，然后列出 3–7 条**可客观判断**的验收标准。标准不能是"质量好"这种话，必须是"能通过 X 命令""包含 A/B/C 三节""在 Y 场景下不报错"这种能验的。

**再拆工作流（workstream）。** 每块工作流标注依赖：互不依赖的并行跑，有前后依赖的排串行。不要把有依赖的活硬塞进并行，那只会互相等。

**然后自动分配角色。** 角色名来自工作流本身，不是固定班底——写文档的任务就别拉"架构师"来凑数。每个角色一张卡：

- **目标**：一句话
- **输入**：它需要什么（文件路径、上游产物、约束）
- **交付物**：**落盘路径**，不是"一段说明"
- **验收标准**：它自己负责哪几条
- **边界**：明确不做什么，防止越界改别人的东西

**规模控制：2–6 个角色。** 超过 6 个就把同质工作流合并；少于 2 个说明这任务不需要组队，直接自己干，别硬凑角色表演。

把以上全部写进 `plan.md`，然后再往下走。

## 阶段 1：并行干活

用 **`workflow` 工具**编排，骨架见 `templates/team-workflow.js`（先读它再写脚本）。

- 无依赖的工作流用 `pipeline()` 跑，**不要用 `parallel()` 造 barrier**——`parallel` 会让所有角色互相等，失去并行的意义。
- 一个角色 = 一次 `agent()` 调用。子代理**看不到本次对话**，prompt 必须自包含：把任务、约束、输入路径、交付路径、验收标准全部写进 prompt。
- **必须给 `schema`**，返回结构化结果（骨架里有 `ROLE_SCHEMA`），否则验收阶段没法机械对照。
- 角色必须把**真实产物写到 `work/<role>/`** 下。只回一段话、不落盘的，视为未完成。
- 角色必须自检并**如实报告未完成项**（`status: partial|blocked` + `open_questions`）。在 prompt 里明确写：禁止假装完成，如实报告比假装完成有价值。

## 阶段 2：产品验收

验收代理**独立**于所有产出者。它的 prompt 里要有：

- 阶段 0 的验收标准原文
- 各交付物的**真实路径**（叫它自己去读，不要给它产出者的总结）
- 明确的对抗性要求：默认去找真缺陷

同时给它**反编造**约束：每一条问题必须带证据（`文件:行`、命令输出、或复现步骤）。没有证据的猜测不算阻塞项。宁可少报，不可编造。

输出 `REVIEW_SCHEMA`：

- `verdict`: `pass` | `fail`
- `criteria[]`: 逐条标准 + 是否达成 + 证据
- `blocking[]`: 阻塞项，每条含 `id / severity / where / why / how_to_fix / owner_role / evidence`
- `non_blocking[]`: 不阻塞交付的改进建议

把这一轮写进 `review/round-N.md`。

## 阶段 3：返工循环

`fail` 时：

1. 按 `owner_role` 把每条阻塞项**路由回责任角色**；归属不清就新开一个角色。
2. **只重跑受影响的工作流**，别把所有角色重跑一遍——浪费且会引入新问题。
3. 重新验收。

**直到 `pass`。** 但要有平台期保护，否则会无限烧下去：

> 连续两轮阻塞项数量**没有下降** → 停止循环，向用户升级。

升级时如实说清楚：卡在什么问题上、已经试过哪些修法、为什么没修好、需要用户做什么决定。这比再跑十轮有意义。循环上限默认 8 轮，`maxRounds` 可调。

## 阶段 4：交付

**只有 `pass` 才交付。** 用用户的语言，按这个顺序：

1. **一句话结论** —— 做完了什么，验收通过
2. **交付物清单** —— 每条带可点击的路径链接；文件类交付物用 `present`
3. **分工回顾** —— 谁做了什么（简短，一段话）
4. **验收结论与证据** —— 产品怎么验的，关键证据
5. **已知限制与未覆盖项** —— 诚实列出没做到的、没测的
6. **建议下一步** —— 可选

**保留 `.dsh-team/<task-slug>/`**，别删——用户以后要追查"当时怎么验的"就靠它。

## 禁止事项

- ❌ 问用户"要哪些角色""要不要我继续"——按流程自己走完
- ❌ 在验收 `fail` 的情况下说"已完成""基本完成"
- ❌ 把子代理的自述当作验收证据
- ❌ 为了显得热闹硬凑角色；2 个够用就别写 5 个
- ❌ 让验收代理同时充当产出者
- ❌ 交付时隐瞒已知缺陷
