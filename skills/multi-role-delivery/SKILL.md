# 多角色组队交付（用户终审版）

```
接单拆解 → 多角色并行干活 → 产品初筛 → 交付 v1 → 用户终审
   ↑                                                    │
   └────────── 不满意就全体返工 ←──────────────────────┘
```

两条底线：

- **全自动**：接单就跑到底。中间不问"要不要继续"、不问"要哪些角色"、不要用户写规范。
- **用户才是终审**：产品说通过，只代表"够格拿给你看"，**不代表完成**。用户说满意才算完成。

## 六条硬性规则

1. **接单立刻 `create_goal`。** 这一步是"全自动"的关键——goal 让会话跨轮自动续跑，用户不用每轮说"继续"。objective 写清交付物和"直到用户明确表示满意才算完成"。
2. **不问角色。** 自己拆、自己定，写进 `plan.md`。只有交付物本身有歧义才回问。
3. **验收者独立于产出者。** 自己验自己等于没验。
4. **证据只看盘上的东西。** 子代理的自述不算证据，必须读文件、跑命令。
5. **用户没满意，绝不说"完成""基本完成"。** 只有 `update_goal complete` 之前的那一次，才叫完成。
6. **只有用户能喊停。** 平台期不是停下来等用户的理由（见阶段 5）。

## 任务目录

接到任务后**第一件事**就是建目录：

```
<cwd>/.dsh-team/<task-slug>/
├── plan.md              # 阶段0：拆解、角色卡、验收标准
├── work/<role>/         # 阶段1：各角色的真实交付物
├── review/round-N.md    # 产品初筛报告
└── feedback/round-N.md  # 用户的意见 + 你把它翻译成的阻塞项
```

## 阶段 0：接单与拆解

**先定义"完成"。** 交付物写成一两句，再列 3–7 条**可客观判断**的验收标准——不能是"质量好"，必须是"能通过 X 命令""包含 A/B/C 三节""在 Y 场景下不报错"。

**再拆工作流。** 标注依赖：互不依赖的并行跑，有依赖的排串行。不要把有依赖的硬塞进并行，那只会互相等。

**然后自动分配角色。** 角色名来自工作流本身，不是固定班底——写文档的任务别拉"架构师"凑数。每个角色一张卡：目标 / 输入 / 交付物（**落盘路径**）/ 验收标准 / 边界。

**规模控制 2–6 个角色。** 超过就合并同质工作流；少于 2 个说明不需要组队，直接自己干，别硬凑角色表演。

全部写进 `plan.md`，然后往下走。

## 阶段 1：并行干活

用 **`workflow` 工具**编排，骨架见 `templates/team-workflow.js`（先读它再写脚本）。

- 无依赖的工作流用 `pipeline()`，**不要用 `parallel()` 造 barrier**——那会让所有角色互相等。
- 一个角色 = 一次 `agent()`。子代理**看不到本次对话**，prompt 必须自包含。
- **必须给 `schema`**，返回结构化结果。
- 角色必须把**真实产物写到 `work/<role>/`**，只回一段话不算完成。
- 角色必须如实报告未完成项（`status: partial|blocked`）。prompt 里写明：禁止假装完成。

## 阶段 2：产品初筛（不是终审）

验收代理**独立**于所有产出者。prompt 里给：验收标准原文、各交付物的**真实路径**（叫它自己读，别给产出者的总结）、明确的对抗性要求。

同时给**反编造**约束：每条问题必须带证据（`文件:行`、命令输出、复现步骤）。没证据的猜测不算阻塞项。宁可少报，不可编造。

输出 `verdict` / `criteria[]` / `blocking[]` / `non_blocking[]`，写进 `review/round-N.md`。

`fail` 就按 `owner_role` 路由回责任角色，**只重跑受影响的工作流**，再筛一次。**内部初筛最多 3 轮**——初筛的作用是把明显不合格的挡在你面前，不是追求完美。3 轮还没过，就带着已知问题交付，如实说明。

## 阶段 3：交付 v1（尽早交付）

**初筛通过就立刻交付，不要憋到完美。** 用户的时间比你的打磨值钱，早点拿到反馈比多打磨三轮有用。

用用户的语言，按这个顺序：

1. **一句话结论** —— 做完了什么
2. **交付物清单** —— 带可点击路径；文件类用 `present`
3. **分工回顾** —— 谁做了什么（一段话）
4. **初筛结论与证据** —— 怎么验的，关键证据
5. **已知限制与未覆盖项** —— 诚实列出
6. **建议下一步** —— 可选

## 阶段 4：用户终审循环 ← 核心

交付完**立刻**用 `ask_user_question` 问一次满意度。这是全程唯一打断用户的地方，成本压到最低：

- question：「这一版满意吗？不满意就直接说哪里不对，我来安排返工，不用你写规范。」
- options：「满意，就这样」/「不满意，我在下面说」

### 用户说满意

`update_goal` 的 `action: complete` → 结束。这是唯一可以宣布"完成"的时刻。

### 用户说不满意

**用户只需要说他哪里不爽，剩下的全是你的活：**

1. **翻译。** 用一次 `agent()` 把用户的大白话转成结构化阻塞项：`what / why / how_to_fix / owner_role / scope`。用户说"看着乱"不是废话——那是排版问题，归排版角色。写进 `feedback/round-N.md`。
2. **判断范围。**
   - 指了**具体点** → 只路由给责任角色。
   - 是**整体性意见**（"感觉不对""不如预期"）→ **全体返工**：所有角色重新过一遍自己的部分。用户的整体感受通常代表一类问题，只修他指出的那一处一定还会被退。
3. **返工。** 调 `workflow` 工具的 `rework` 模式，跑受影响的工作流。
4. **重新初筛** → **交付 vN**。
5. **再问一次满意度。**

交付 vN 时**突出"这轮改了什么"**——增量清单，让用户一眼看出他的意见有没有被听进去。

**这个循环没有轮数上限，只有用户能喊停。**

### 平台期怎么办（不要停下来等用户）

内部初筛连续两轮问题数没下降，**不要**停下来问用户——那正是"半自动"的来源。换打法继续：

- 换角色：把出问题的角色换掉，或新开一个"唱反调"角色专门挑刺
- 换方案：同一目标换一条实现路径重做
- 拆更细：把卡住的大块拆成小块逐个解决
- 加约束：回到 `plan.md` 补一条之前漏掉的验收标准

只有**真正的歧义**（用户要什么本身说不清）才回问用户，而且问的时候要给出你的默认判断和理由。

## 全自动检查清单

跑完一轮前自查：

- [ ] 接单时就 `create_goal` 了吗？
- [ ] 全程除了满意度那一次，没问过用户任何问题吗？
- [ ] 没有说过"要不要我继续""需要我做什么"吗？
- [ ] 平台期是换打法，而不是停下来等用户吗？
- [ ] 用户没说满意之前，没说过"完成"吗？

## 禁止事项

- ❌ 在用户说满意之前宣布完成
- ❌ 每轮停下来说"要不要继续""还需要我改什么"
- ❌ 问用户"要哪些角色"
- ❌ 用户不满意时只修他指出的那一处（整体性意见必须全体返工）
- ❌ 把子代理的自述当作验收证据
- ❌ 为了显得热闹硬凑角色；2 个够用就别写 5 个
- ❌ 让验收代理同时充当产出者
- ❌ 交付时隐瞒已知缺陷
