# 多角色组队交付（multi-role-delivery）

给 DSH 用的一个技能：**你说任务，它自己组队干活，产品初筛后就拿给你看；你不满意，它自动返工，直到你说满意为止。**

```
接单拆解 → 多角色并行干活 → 产品初筛 → 交付 v1 → 你终审
   ↑                                                │
   └──────────── 不满意就全体返工 ←────────────────┘
```

## 它解决什么

一个人干活的默认模式是：一件事做完再做下一件，没人检查，而且你得盯着它、催它、反复解释。这个技能把它换成：

- **全自动**：接单就建 goal，会话跨轮自动续跑。中间不问"要不要继续"、不问"要哪些角色"、不要你写规范。
- **自动分配**：你说任务，不说角色。它拆解完自己决定需要哪些角色、谁跟谁并行。
- **并行干活**：互不依赖的工作流同时开工，不是排队。
- **产品初筛**：一个独立代理专门挑毛病，必须读盘上的真实产物、真跑命令，每条问题都要带证据。初筛只负责把明显不合格的挡在你面前。
- **你才是终审**：产品说通过 ≠ 完成。只有你说满意才算完成。
- **改到你满意**：你不满意时，只需要说哪里不爽——**不用写规范**。它会把你的大白话翻译成结构化返工项、判断范围、安排返工、重新交付。循环没有轮数上限，只有你能喊停。
- **整体性意见触发全体返工**：你说"感觉不对"，它不会只修你指出的那一处——那是整体信号，所有角色一起重做。

## 安装

先 clone，再用 junction 挂到 DSH 技能目录（不要复制文件，复制会让仓库和已装副本逐渐不同步）：

```powershell
git clone https://github.com/XCool-603/multi-role-delivery.git C:\Work\multi-role-delivery

New-Item -ItemType Junction `
  -Path "$env:DSH_HOME\skills\multi-role-delivery" `
  -Target "C:\Work\multi-role-delivery\skills\multi-role-delivery"
```

`$DSH_HOME` 默认是 `~/.dsh`。装好后技能会在会话的技能目录里立刻出现，无需重启。

> junction 依赖 clone 下来的目录存在，删掉或移动它技能就会失效。想更新就 `git pull`，改动即时生效，不用重装。

## 让所有任务都过这道门

技能是"按需触发"的——不说触发词，它不会自己上。要让**每个任务**都过门，得把规则挂到 DSH 每次会话都会注入的地方：**用户全局的 `$DSH_HOME/AGENTS.md`**。

仓库里附了模板 `templates/AGENTS.template.md`，复制过去即可：

```powershell
Copy-Item skills\multi-role-delivery\templates\AGENTS.template.md "$env:DSH_HOME\AGENTS.md"
```

已经有 `$DSH_HOME\AGENTS.md` 的话，把内容追加进去，别覆盖。

> 模板特意不叫 `AGENTS.md`——否则它自己会被当成工作区指令文件，在本仓库里重复注入一份。

装好后**每个新会话**都会带上这条纪律：有交付物的任务必须先加载本技能、走完整流程、过了内部初筛才能交到你面前。

> `AGENTS.md` 在每个会话都占上下文，所以模板刻意写得很短（约 1KB）；详细流程放在技能里按需加载。
> 改动 `AGENTS.md` 后已有会话要**新开或重启**才生效——DSH 只在第一个请求注入这条基线。

### 分级，不是一律上重流程

模板按规模分档：琐碎问答直接答（只做自检），有交付物的走完整流程，大任务再加用户终审循环。对"现在几点"这种问题拉起六个角色是纯浪费。拿不准就往上靠一档。

## 用法

直接说任务就行，触发词包括"多角色""组队""分工""并行""让产品检查""交付给我""改到我满意""全自动"等。例如：

> 帮我把这个项目整理成一份对外介绍文档，多角色分工做，改到我满意为止。

它会：

1. 建 `.dsh-team/<task-slug>/` 任务目录，并 `create_goal` 让会话自动续跑
2. 写 `plan.md`：验收标准、工作流拆解、角色卡
3. 用 `workflow` 工具并行跑各角色，产物落在 `work/<role>/`
4. 独立初筛代理逐条核对，报告落在 `review/round-N.md`
5. 初筛通过就交付 v1
6. **问你一次「满意吗」**——这是全程唯一打断你的地方
7. 你说不满意 → 意见落 `feedback/round-N.md` → 返工 → 交付 vN → 再问一次
8. 你说满意 → 结束

## 目录结构

```
skills/multi-role-delivery/
├── SKILL.md                      # 流程规范（技能本体）
└── templates/
    ├── team-workflow.js          # workflow 工具编排骨架
    └── AGENTS.template.md        # 全局交付门，复制到 $DSH_HOME/AGENTS.md
```

`templates/team-workflow.js` 支持两种模式：

```js
// 首次开工
{ mode: 'initial', task, taskDir, criteria: [...], roles: [...], gateRounds: 3 }

// 用户不满意之后
{ mode: 'rework', task, taskDir, criteria, roles, userFeedback: '用户原话', startRound: 2 }
```

`rework` 模式会先用一个代理把你的原话**分诊**成结构化返工项（含 `owner_role` 和 `global_redo` 范围判断），再按范围路由返工，最后走内部初筛门。

## 设计取舍

- **产品降为初筛，用户升为终审。** 产品代理看不到你的审美和真实需求，让它当终审必然"它说好你说不好"。它只负责挡明显不合格的。
- **内部初筛限 3 轮。** 初筛的作用是别让垃圾先送到你面前，不是追求完美。3 轮还没过就带着已知问题交付并如实说明——你的时间比它的打磨值钱。
- **尽早交付。** 初筛一过就给你看，不憋到完美。早拿到反馈比多打磨三轮有用。
- **平台期换打法，不停下来问你。** 初筛连续两轮问题数没下降，就换角色、换方案、拆更细、补约束——而不是停下来问用户。这正是"半自动"和"全自动"的分界线。
- **角色数限制 2–6 个。** 超过就合并同质工作流；少于 2 个说明不需要组队，直接干，不硬凑角色表演。
- **验收者必须独立于产出者。** 自己验自己等于没验。
- **只认盘上的证据。** 子代理的自述不算数，必须读文件、跑命令。
- **任务目录保留。** 以后要追查"当时怎么验的""你提的意见怎么改的"靠它。
